# Conductor に Agent Teams を導入した話
## キーマップ変更を 3 エージェントで分業する

---

## 背景：なぜ分業が必要だったか

ZMK キーマップの変更は一見シンプルに見える。`config/monokey.keymap` を開いて、binding を書き換えるだけだ。

しかし実際にやってみると、ミスが起きやすいポイントがいくつかある：

- **key-position の計算ミス**：40 キーをインデックスで指定するため、行・列を数え間違えやすい
- **`&trans` の抜け漏れ**：使用しないキーは `&trans` にする規約があるが、新しいレイヤーを追加するときに忘れやすい
- **コンボ競合**：既存のコンボと key-position が重なると、意図しない動作になる

さらに問題なのが「1 つのセッションで分析・実装・検証を全部やると context が長くなる」点だ。セッション後半になると、序盤に読んだキーマップの状態と現在の状態が混同されやすくなる。

そこで試したのが、Claude Code の **Agent Teams** 機能を使った役割分担だ。

---

## Agent Teams とは

Claude Code の実験的機能で、`settings.json` に以下を追加するだけで有効になる：

```json
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}
```

有効化すると、`.claude/agents/` ディレクトリに置いた Markdown ファイルが「エージェント定義」として読み込まれる。

```
.claude/agents/
├── architect.md
├── implementer.md
└── reviewer.md
```

各ファイルは YAML frontmatter でエージェントの名前・説明・使用ツールを宣言できる：

```markdown
---
name: architect
description: キーマップの現状分析と変更仕様の策定を行うエージェント
tools: Read, Grep, Glob
---

あなたは...（以下、エージェントへの指示）
```

**ポイントは `tools` で使えるツールを制限できること**。これが「役割の境界」として機能する。

---

## 3 エージェントの設計

### エージェント一覧

| エージェント | 許可ツール | 役割 |
|---|---|---|
| **Architect** | Read, Grep, Glob | 現状分析・変更仕様の策定 |
| **Implementer** | Read, Edit, Write | 仕様に従って keymap を編集 |
| **Reviewer** | Read, Grep, Glob, Bash | 編集後の整合性チェック |

### ツール制限の意図

- **Architect は Edit を持たない** → 分析中に誤って編集してしまう事故がなくなる
- **Implementer は Bash を持たない** → ビルドや外部コマンドを勝手に実行できない。変更仕様の適用だけに集中する
- **Reviewer は Bash を持つが Edit は持たない** → 検証のためのコマンド実行はできるが、直接修正はしない。問題を見つけたら Leader（メインセッション）に報告する

## ワークフロー

```
ユーザー「〇〇キーを変えて」
    │
    ▼
[Architect]
  - config/monokey.keymap を読む
  - 変更対象の key-position を特定
  - 変更仕様表を出力（before/after のテーブル）
    │
    ▼ 変更仕様を受け取る
[Implementer]
  - 仕様通りに bindings を書き換える
  - 変更後のブロックを報告
    │
    ▼ 編集完了報告
[Reviewer]
  - キー数（各レイヤー 40 キー）を確認
  - コンボ競合をチェック
  - hold-tap 設定（mt/lt）を検証
  - レイヤー透過チェーンの妥当性を確認
    │
    ▼ チェック結果
Leader が確認 → /flash でコミット・push・ビルド
```

## 各エージェントの出力フォーマット

それぞれのエージェントには決まった出力フォーマットを定義している。こうすることで次のエージェントが情報を受け取りやすくなる。

### Architect の出力例

```
## 変更仕様

### 対象レイヤー: FUNCTION

| key-position | 現在のbinding | 変更後のbinding | 備考 |
|---|---|---|---|
| 11 | &kp MINUS | &kp EQUAL | = に変更 |

### コンボへの影響
- なし

### 注意点
- FUNCTION レイヤーの右手側の変更のみ
```

### Reviewer の出力例

```
## レビュー結果

### ステータス: ✅ OK

### チェック結果
| 項目 | 結果 | 詳細 |
|---|---|---|
| キー数 | ✅ | 全レイヤー 40 キー確認 |
| コンボ競合 | ✅ | 既存コンボとの重複なし |
| hold-tap設定 | ✅ | mt flavor=balanced, quick-tap-ms=175 |
| レイヤー透過チェーン | ✅ | &trans の使用に問題なし |

### 推奨アクション
- コミット・push して問題なし
```

## 周辺整備：安全に動かすために

Agent Teams を導入したついでに、`settings.json` の `deny` ルールも強化した：

```json
{
  "permissions": {
    "deny": [
      "Bash(rm -rf*)",
      "Bash(git reset --hard*)",
      "Bash(git push --force*)",
      "Bash(git branch -D*)"
    ]
  }
}
```

force push やブランチ削除を禁止することで、エージェントが誤操作するリスクを減らしている。

また、git push 後に GitHub Actions のビルド結果を自動確認する PostToolUse フックも設定済みだ。push されたタイミングで 2 分 30 秒待機してからビルド結果を確認するよう促してくれる（過去 25 回の実行時間の中央値が 113 秒だったため）。

---

## まとめ

Agent Teams を使って「分析→実装→検証」を 3 エージェントに分担させた主なメリットは：

1. **ツール制限による役割の明確化** — 設定ファイルを書くだけで「このエージェントは編集できない」という制約を強制できる
2. **context の分離** — 各エージェントは自分の役割に必要な情報だけで動作する
3. **出力フォーマットによる引き継ぎの明確化** — 仕様表・変更報告・チェック結果がそれぞれ定型化されているので、次のエージェントが迷わない

設定ファイルはすべて `.claude/` 配下に git 管理されているため、ブランチをまたいでも同じ動作が再現できる。
